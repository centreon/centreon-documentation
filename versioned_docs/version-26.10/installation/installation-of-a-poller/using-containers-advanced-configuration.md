This page covers optional configuration for a poller [deployed in a
container](./using-containers.md),
beyond the default `centengine` and `gorgone` services.

## Allow the poller to send email notifications

This section applies if you want your poller to be able to send notifications.

A poller in a container has two different ways to send email
notifications, so you can use whichever fits your infrastructure:

* A [native SMTP command](#option-1-native-smtp-command), using the `mail` command (from `mailutils`)
  relayed through `msmtp`. 
* The [**centreon-plugin-notification-email** connector](#option-2-centreon-plugin-notification-email-connector).

### Option 1: Native SMTP command

This is the most common way of [sending notifications](../../alerts-notifications/notif-configuration.md).

The native SMTP command needs an SMTP relay to send emails. Configure it with environment variables on the `centengine` service in the docker-compose.

| Variable | Effect |
|----------|--------|
| `SMTP_HOST` | Address of the SMTP relay. Required for the native SMTP command: notifications are silently not sent while this is empty. |
| `SMTP_PORT` | Port of the SMTP relay (default: `25`). |
| `SMTP_FROM` | Sender address of outgoing notification emails (used for both the envelope sender and the `From:` header). |
| `SMTP_TLS` | Set to `on` to use TLS when connecting to the relay (default: `off`). |

The `docker-compose.yaml` generated by the install script loads these
variables from a `.env.smtp` file, located in the same directory:

```yaml
services:
  centengine:
    # ...
    env_file:
      - .env
      - .env.smtp
```

The install script creates `.env.smtp` empty, and never overwrites it when
you run it again. Store your variables in this file:

```shell
# .env.smtp
SMTP_HOST=smtp.example.com
SMTP_PORT=25
SMTP_FROM=centreon-engine@example.com
SMTP_TLS=off
```

Restart the `centengine` service (`docker compose up -d`) after changing these variables.

`mailutils` and `msmtp` are pre-installed in the image. At startup,
`centengine` writes an `msmtp` configuration from the `SMTP_*` variables
above, so `/usr/bin/mail` sends through your relay with no further setup.

> In Centreon 26.10.0, the install script does not create `.env.smtp` and
> the generated `docker-compose.yaml` does not reference it: add the
> `env_file` lines above to the `centengine` service yourself. The emails are
> sent from `centreon-engine@<container host name>`, whatever the value of
> `SMTP_FROM`.

### Option 2: centreon-plugin-notification-email connector

The connector's SMTP relay settings are plain command-line options, so you can set them directly in the command.

The connector is pre-installed under `$CENTREONPLUGINS$` (usually
`/usr/lib/centreon/plugins/`), as `centreon_notification_email.pl`. Its
`--smtp-address`, `--smtp-port` and `--from-address` options take your relay
directly, no environment variable needed.

The connector picks between its host and service notification templates
based on whether `--service-description` is set, so the **same command_line**
can be used as both the host and the service notification command. Replace
the SMTP, Centreon URL, and token placeholders below with your own, then
define it on the **Configuration > Commands** page:

```shell
$CENTREONPLUGINS$centreon_notification_email.pl --plugin=notification::email::plugin --mode=alert --to-address='$CONTACTEMAIL$' --host-address='$HOSTADDRESS$' --host-name='$HOSTNAME$' --host-alias='$HOSTALIAS$' --host-state='$HOSTSTATE$' --host-output='$HOSTOUTPUT$' --host-attempts='$HOSTATTEMPT$' --max-host-attempts='$MAXHOSTATTEMPTS$' --host-duration='$HOSTDURATION$' --date='$SHORTDATETIME$' --type='$NOTIFICATIONTYPE$' --service-description='$SERVICEDESC$' --service-displayname='$SERVICEDISPLAYNAME$' --service-state='$SERVICESTATE$' --service-output='$SERVICEOUTPUT$' --service-longoutput='$LONGSERVICEOUTPUT$' --service-attempts='$SERVICEATTEMPT$' --max-service-attempts='$MAXSERVICEATTEMPTS$' --service-duration='$SERVICEDURATION$' --host-id='$HOSTID$' --service-id='$SERVICEID$' --notif-author='$NOTIFICATIONAUTHOR$' --notif-comment='$NOTIFICATIONCOMMENT$' --centreon-url='https://central.example.com' --smtp-address='smtp.example.com' --smtp-port='25' --from-address='centreon-engine@example.com' --centreon-user='admin' --centreon-token='your-autologin-key' --smtp-nossl
```

* `--centreon-url`, `--centreon-user` and `--centreon-token` (a Centreon
  autologin key, **Administration > Accounts > your user > Security**) make
  the email link back to the resource and embed its performance graph. Omit
  all three if you don't need that - the email is still sent.
* `--insecure` skips TLS certificate verification when fetching that graph,
  useful when `--centreon-url` uses a self-signed certificate.
* Add `--smtp-user`/`--smtp-password` if your relay requires authentication,
  and drop `--smtp-nossl` to use TLS.

> Storing `--centreon-token` in a command definition puts it in plain text
> in Centreon Engine's configuration. Use a token scoped to a dedicated,
> low-privilege account rather than an administrator's.

These options can also use the `$SMTPADDRESS$`, `$SMTPPORT$` and `$SMTPFROMADDRESS$`
poller resource macros. Define their values on the
**Configuration > Pollers > Resources** page: the container does not change
them. The `SMTP_*` variables (see Option 1) are only used by the native SMTP
command.

> In Centreon 26.10.0, these macros are overwritten at each container start
> with the values of the `SMTP_HOST`, `SMTP_PORT` and `SMTP_FROM` variables,
> and are emptied when these variables are not set.

## Allow the poller to use custom plugins for monitoring

This section only applies if you want to use your own custom plugins for monitoring. No action is needed to use the official Centreon monitoring connectors.

The `centengine` container can install custom check scripts and extra APT dependencies without rebuilding the image.

In the generated `docker-compose.yaml`, add the following volumes to the `centengine` service :

```yaml
    volumes:
      # Custom plugin scripts (must be executable)
      - ./custom-plugins:/usr/lib/nagios/plugins/custom:ro
      # Extra APT packages, installed at startup
      - ./custom-deps.json:/etc/centreon-engine/custom-deps.json:ro
```

* Create a **custom-plugins** directory and store your custom plugin scripts there. The container will copy them to `/usr/lib/nagios/plugins/custom`.
* If your plugin needs system dependencies, you must declare them in a `custom-deps.json` file. For example:

  ```json
  {
    "apt": ["snmp", "jq"]
  }
  ```

  This file is read when the container starts, and watched for changes
  afterward: editing it on the host triggers an automatic install of the
  listed packages, with no need to restart the container. Package
  installation runs in the background, so `centengine` is not blocked while
  it happens.

### Baking dependencies into a custom image

If you have a large number of dependencies, you can build a custom image on top of the official one instead of adding the dependencies one by one to the `custom-deps.json` file. Your custom image will be deployed using the docker-compose.

<!-- Instead of installing dependencies at container startup, you can build your
own image on top of the official one and install everything at build time: -->

```dockerfile
FROM ghcr.io/centreon/centreon-engine:26.10

RUN sudo apt-get update && sudo apt-get install -y --no-install-recommends \
      snmp \
      jq \
    && sudo apt-get clean
```

Build it, then reference it as `ENGINE_TAG` (or override the `image:` value
directly) in your `docker-compose.yaml`. The main advantage of this approach
is startup time: when a poller needs many dependencies, installing them once
at build time is faster than installing them every time the container starts
via `custom-deps.json`.

## Allow the poller to monitor VMware resources

Follow this procedure before you deploy a poller in a container using the `--with-vmware` option.

Monitoring VMware infrastructure requires the proprietary VMware Perl SDK:
the daemon cannot start at all without it, even with plain-text credentials.
Because the SDK cannot be redistributed for licensing reasons, the
`centreon-vmware` container image is not published on a registry. The
`docker-compose.yaml` generated with `--with-vmware` builds it locally, on the
container host, from a `centreon-plugins` checkout, the first time the stack
starts.

1. Clone `centreon-plugins` on the container host, in the directory where you
   will run the install command:

   ```shell
   git clone https://github.com/centreon/centreon-plugins.git
   ```

   To use another location, add `--vmware-path <path>` to the install command.

2. Download the SDK archives from the Broadcom developer portal (see the
   [prerequisites of the VMware ESX monitoring
   connector](/pp/integrations/plugin-packs/procedures/virtualization-vmware2-esx#prerequisites)
   for instructions), and place them in the `sdks-vmware` directory of the
   checkout:

   * `VMware-vSphere-Perl-SDK-7.0.0-17698549.x86_64.tar.gz`
   * `vsan-sdk-perl.zip`

3. Run the install command with `--with-vmware`. The install script checks
   that the checkout and the SDK archives are present before generating the
   files, and stops with an error message if they are missing.

The image is built only if it does not exist yet. To rebuild it, for example
after updating your `centreon-plugins` checkout, run:

```shell
docker compose build centreon-vmware
docker compose up -d
```

> The build downloads the latest package from Centreon's stable APT
> repository. To pin a specific release, add a `VERSION` build argument to
> the `centreon-vmware` service's `build:` section in `docker-compose.yaml`
> (`args: [VERSION=<version>]`).

> In Centreon 26.10.0, the generated `docker-compose.yaml` does not build the
> image: build it yourself before running the install command, with
> `docker build --file .github/docker/connector/Dockerfile.connector-vmware --tag connector-vmware:local .`
> from the root of the `centreon-plugins` checkout.

## Allow the poller to receive data from Centreon Monitoring Agents (CMA)

Add `--with-cma` to the poller install command so that `centengine` can accept
connections from the Centreon Monitoring Agent over OpenTelemetry gRPC. Using `--with-cma`
adds the following to the `centengine` service in the docker-compose:

```yaml
    volumes:
      - poller-cma-pki:/etc/pki/centreon-engine
    ports:
      - 4317:4317
```

The first time it starts, `centengine` generates the poller's certificate
authority (CA) in the `poller-cma-pki` volume. The CA is kept when the
container is recreated, so agents that already trust it keep working.

The CA is issued for the host name of the `centengine` container, set with
`--cma-hostname` (default: `centengine`). Agents must reach the poller using
this name:

1. Add `--cma-hostname <hostname>` to the install command, where `<hostname>`
   is the host name of the container host, as resolved by the monitored hosts
   (for example `poller1.example.com`).
2. Configure the agents following
   [Setting up the agent's environment](../../cma/cma-setup.md), using this
   host name as the poller's address.

To change the host name later, edit `ENGINE_HOSTNAME` in `.env`, delete the
`poller-cma-pki` volume (`docker volume ls` shows its full name), then run
`docker compose up -d`. A new CA is generated: configure the agents again
with the new fingerprint (see
[Removing the CA from the host](../../cma/cma-setup.md#removing-the-ca-from-the-host)).

> In Centreon 26.10.0, `--with-cma` mounts `./certs/poller.crt` and
> `./certs/poller.key` instead of the `poller-cma-pki` volume, and
> `--cma-hostname` does not exist: generate the certificates yourself
> following [Configuring certificates](../../cma/cma-certificates.md).

## Set the log level of the services

The following variables in the generated `.env` file set the log level of
Gorgone and `centreontrapd`. Run `docker compose up -d` after changing them.

| Variable | Effect |
|----------|--------|
| `GORGONE_LOG_LEVEL` | Log level of Gorgone: `fatal`, `error`, `warning`, `notice`, `info` or `debug` (default: `info`). |
| `CENTREONTRAPD_LOG_LEVEL` | Log level of `centreontrapd`, with `--with-snmptrap` only (default: `error`). |

When you run the install command again and `.env` is overwritten, these
variables are reset to their default value. To keep your value, export the
variable before running the command (for example
`export GORGONE_LOG_LEVEL=debug`).

## Using Podman

The install script also supports Podman, rootful or rootless (run as a
regular user). It uses `podman compose` or `podman-compose` when Docker is not
available, and checks the following before generating the files:

* If the compose command relies on `docker-compose`, the Podman API socket
  must be running. Enable it with `sudo systemctl enable --now podman.socket`
  (rootful) or `systemctl --user enable --now podman.socket` (rootless).
* In rootless mode with `--with-snmptrap`, the user must be allowed to publish
  port 162:

  ```shell
  echo 'net.ipv4.ip_unprivileged_port_start=162' | sudo tee /etc/sysctl.d/99-centreon-poller.conf
  sudo sysctl --system
  ```

* In rootless mode, the stack stops when the user logs out unless lingering
  is enabled for this user (the script displays a warning).
* With `--with-vmware`, Podman does not support the `COPY --link`
  instruction of the `centreon-vmware` Dockerfile. Remove the `--link` flag
  from the Dockerfile in your `centreon-plugins` checkout:

  ```shell
  sed -i 's/COPY --link /COPY /' .github/docker/connector/Dockerfile.connector-vmware
  ```

Podman does not restart containers when the host reboots. To start the
stack again automatically after a reboot, run:

* In rootful mode:

  ```shell
  sudo systemctl enable podman-restart.service
  ```

* In rootless mode:

  ```shell
  sudo loginctl enable-linger $(id -un)
  systemctl --user enable podman-restart.service
  ```

> Hosts where SELinux is in enforcing mode are not supported yet with Podman:
> the containers cannot access the volumes they share.

> Podman is not supported in Centreon 26.10.0.
